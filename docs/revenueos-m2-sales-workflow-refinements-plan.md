# M2 — Sales Workflow Refinements: audit and implementation plan

Status: READ-ONLY AUDIT AND PLAN, 2026-10-08. No file, database, migration, commit or running service was changed to produce this. M1 is closed (frontend `944b8ea`, CP2 `de67e48`, CP3 activated) and is not touched by M2.

Inspected: backend `1a27b1e` (opportunities, leads, lead timeline, WhatsApp/webhook lead creation, customer GST values), frontend `944b8ea` (opportunity detail, dashboard board, lead forms/lists/detail, Toast, ConfirmDialog, Modal, QuickActions), and the real database (read-only: schema, the 12 leads, 4 opportunities, timeline events, permissions).

Foundation classification used below: **Reuse** (adequate as is), **Extend** (exists, needs additions), **Replace** (exists but wrong), **New**, **Out of scope**.

---

## 0. Facts from the inspection that shape the plan

1. **The stage event already exists and already holds text.** `OpportunitiesService.updateStage` writes one `LeadTimeline` row, `action = OPPORTUNITY_STAGE_CHANGED`, `source = SYSTEM`, `actorId` = the signed-in user, in the same transaction as the compare-and-set stage update. Its `remarks` column holds the system sentence `Opportunity "TEST 1": Qualified → Proposal`. A person's remark therefore cannot simply be put in `remarks` without mixing two things. The `UpdateOpportunityStageDto` is `{ fromStage, toStage }` and the ValidationPipe has `whitelist` + `forbidNonWhitelisted`, so today any extra field (a `remarks`) is rejected with 400.
2. **`Lead` has no location columns at all** (16 columns: name, company, email, phone, alternatePhone, source, assignee, status, lifecycle fields). The frontend "City" is `Lead.uiContext.city`, a UI-only block that `RealLeadRepository` never sends (stated in its header). In real mode the Edit Lead dialog still shows a City box, whose value is discarded; the form labels the block "Stored locally for this demo". The Leads list's City filter is built from `uiContext.city`, so in real mode it has no options.
3. **Real phone numbers are inconsistent.** Of 12 real leads: 5 are 10-digit Indian numbers with no country code (`9876543210`), 5 are WhatsApp-created numbers that include `91` (`919888777666`), 1 has a space (`97175 93074`), none has a `+`. `QuickActions` builds `https://wa.me/<all digits>` and `tel:<digits>`. For a 10-digit number `wa.me/9876543210` is not a valid chat link (wa.me needs the country code), and `tel:919888777666` is dialled without `+`. So the existing behaviour already assumes the stored number carries its country code, and is wrong for the 5 leads that were typed in nationally. No lead has a country recorded to correct this with.
4. **Toast is already the app's feedback mechanism** and is widely used: 67 `toast.show(message, icon)` calls in 37 files (39 `check`, 11 `alert`, 5 `close`, 1 `cal`). It is already bottom-right with a full-width mobile layout, a 3.2 s timeout, reduced-motion handling and a z-index above modals. It has no variants, no screen-reader announcement, no dismiss control, no pause, no stacking limit.
5. **Searchable selects do not exist.** The only precedent is a native `<datalist>` for customer type (free text with suggestions). There is no combobox/listbox component.
6. **The India state list already exists twice** and agrees: backend `GST_STATES` (`customer-gst-values.ts`: 36 states/UTs plus code 97 "Other Territory") and a frontend copy in `customerLifecycle.ts`.
7. **No display name on the client.** `AuthUser` is `{ id, email, role, permissions }` decoded from the token; there is no `/auth/me`. The history shows the actor's full name (backend selects it), but a dialog can only show the signed-in email/role.
8. **Stage-change entry points (frontend), exhaustively:** the Opportunity detail page (Move forward, Move back, Mark Lost, Mark Won, all through `ConfirmDialog` with no note) and the dashboard Kanban "snapshot" board (drag; `Mark Won` is confirmed, every other drop is immediate with no dialog; the board has no Lost column). Nothing else calls `updateStage` (the Lead Pipeline board moves lead status, not opportunity stage; no backend flow changes an opportunity's stage except this endpoint).
9. **Other writers of `Lead`** (so a new field is not silently skipped): `POST/PATCH /leads` (service passes the DTO straight to Prisma), the WhatsApp bot (creates a lead with `phone = incoming number`), the webhook importer (maps connector fields), `lead-status` and `lead-assignments`. Only the first is a person-entered path.

| **Proposed UX** | One shared `OpportunityStageDialog` for every entry point: title names the action ("Move to Proposal", "Mark Won", "Mark Lost", "Move back to Qualified"), a clear transition line `Qualified → Proposal` with the deal title, the existing warning for final stages, one optional textarea "Remark (optional)" with a character counter (limit 500, same as other reasons in RevenueOS), the line "Recorded under <your email>", and Cancel/Confirm. | **Migration** | `20261010_crm_leadtimeline_user_remark.sql`: `ALTER TABLE "LeadTimeline" ADD COLUMN IF NOT EXISTS "userRemark" TEXT;` Idempotent, no pre-flight data condition, rollback = `DROP COLUMN` (loses remarks entered since; copy first). Existing rows stay null; nothing backfilled. |
| **Tests** | Backend: DTO (blank→null, 501 chars rejected, extra field rejected, null/absent accepted), service (remark on the event, null when absent, no event on conflict/forbidden/invalid move, event count and actor unchanged), controller guard unchanged, write-path guard (only `updateStage` writes the column). ## 2. Lead Location

| | |
|---|---|
| **Current implementation** | None in the backend. Frontend: `Lead.uiContext.city` (mock/UI-only) used by the Edit Lead dialog (City box), Leads list (subtitle, City filter, search), Lead detail header. `LeadForm` collects only Product/Interest and Remarks as local context. `RealLeadRepository.create/update` send six fields and drop `uiContext`. |
| **Existing data / API / schema** | `Lead` columns listed in §0.2. 12 real leads, all with no location. India state list exists (backend `GST_STATES`, frontend copy). No country list anywhere. Phone is free text, validated only as non-empty. |
| **Exact gaps** | No persisted location; `CreateLeadDto`/`UpdateLeadDto` reject unknown fields; no searchable select; no country dataset; the City box in Edit Lead silently discards input in real mode; list filter/subtitle/detail read the mock field; no rule tying state to India. |
| **Classification** | Lead DTOs/service/schema: **Extend**. `uiContext.city`: **Replace** (remove from the type; real fields instead; mock seed cities become real fields). India states: **Reuse** (single list, mirrored with a parity test). Country list: **New** (ISO 3166-1 alpha-2 code + English name + calling code). Searchable control: **New** (`Combobox`). `LeadForm`, `EditLeadDialog`, leads list/detail: **Extend**. `uiContext.productInterest/remarks`: **Out of scope** (remain demo-only, still labelled). |
| **Proposed data model** | `Lead."country" TEXT NULL` (ISO alpha-2, upper case; `IN` = Domestic/India), `Lead."state" TEXT NULL` (the canonical state name from the existing list; only for `IN`), `Lead."city" TEXT NULL` (free text, ≤100, "city / specific location"). Domestic vs International is derived from `country`, not stored twice. `NULL` everywhere = "not recorded"; **no lead is assumed Indian**. |
| **Validation (backend, authoritative)** | `country`: one of the ISO codes. `state`: required when `country = IN`, one of the 36 names (code 97 "Other Territory" excluded), and **rejected** when country is not IN. `city`: optional, trimmed, ≤100. Group semantics on `PATCH`: the service validates the *merged* result (existing + change), so switching a lead from India to another country must clear the state in the same request, and a state can never be left on a foreign lead. Absent fields leave the stored values alone; the clients never send `uiContext`. DB `CHECK` as the last word: no state without `IN`; no city/state with a null country. |
| **Proposed UX** | New Lead and Edit Lead get a "Location" section: a two-option segmented control **India (domestic) / International**; India → **State** (searchable combobox, 36 options) + **City / location**; International → **Country** (searchable combobox, ~249 options, matches name or code) + **City / location**. No default is applied silently on edit; an existing lead with no location shows "Not recorded" and the control starts unselected. Combobox follows the WAI-ARIA combobox pattern (labelled input, listbox, up/down/Enter/Escape, type-ahead filter, announces result count, 44 px options on touch, becomes a full-width sheet on mobile). Lead detail shows the location line and replaces "company · city". Leads list: state/country and city filters become real; subtitle and search read the real fields. Manual creation: country (and state when India) is asked for; whether it is *required* is decision D2 below. |
| **WhatsApp / contact impact** | Today wa.me/tel build from the stored digits and assume they include the country code (§0.3). With a country on the lead, a pure helper `contactNumber(phone, country)` can say: country IN and a 10-digit number → `+91…`; a number already starting with the calling code → unchanged; unknown country → current behaviour (never guessed). M2 **provides the country context and the helper** and wires it into the Lead and Opportunity `QuickActions` only (decision D3: this also fixes `wa.me` for the 5 real nationally typed Indian numbers *once their lead has a country*). It does **not** rewrite stored phone numbers, does not infer a country from a number, and builds no WhatsApp Business API integration (M4b). The WhatsApp bot and webhook importer keep creating leads with no location; mapping connector fields to location is future work. |
| **Backend / schema impact** | **Yes (additive).** Three nullable `Lead` columns + CHECK; `CreateLeadDto`/`UpdateLeadDto` gain the three fields with the validation above; new backend constant file for the ISO country codes (names live in the frontend; a parity test keeps the code sets equal); `leads.service` create/update validate and write them; lead responses already return all scalar columns, so `GET /leads`, `GET /leads/:id` and `GET /opportunities` (embedded lead) carry them with no query change. |
| **Permissions / auth** | None new: `leads.create` / `leads.edit`. |
| **Migration** | `20261010_crm_lead_location.sql`: three `ADD COLUMN IF NOT EXISTS` + a named `CHECK` (idempotent; no pre-flight data condition because every existing row is null). Rollback = drop the check and columns (location entered since is lost; copy first). **No backfill.** |
| **Tests** | Backend: DTO (each field, lengths, case), service (IN needs state, non-IN rejects state, invalid code/state, merged PATCH semantics, legacy null leads still editable without location, deactivated lead refused as today), write-path guard (only `LeadsService` writes location), scratch-DB HTTP run. Frontend: pure location rules, dataset parity vs backend (states and country codes), combobox logic (filter, ranking, keyboard model) and static markup (roles/aria), forms (domestic/international switching, clearing state when switching, payload shape), repository parity (real sends the fields, mock stores them), list filters/subtitle/detail, contact helper (10-digit IN, already-prefixed, unknown country untouched), a source guard that no component reads `uiContext.city`, and all existing suites. |
| **Browser verification** | Scratch clone of the real DB: create domestic and international leads, edit between types, searchable select by keyboard and touch, filters, persistence after reload, a legacy lead with no location, view-only user, 360–1280 px × light/dark, overflow sweep, console/network. |
| **Real-DB activation** | Additive migration; the 12 real leads stay "Not recorded" (no backfill; any location is then entered by users through the UI). Backend rebuild/restart + client regeneration + frontend rebuild. Verification on the real stack is read-only plus refused writes (a lead create/edit with an invalid location returning 400 must change nothing); successful creates stay on scratch. |
| **Explicit exclusions** | Inferring country or state from a phone number, name or source; backfilling existing leads; address lines/pincode/geo-coordinates; customer or GST-registration addresses (separate, already governed); WhatsApp Business API, bot or webhook location capture; rewriting stored phone numbers; Product/Interest and Remarks (remain demo-only); field-level location diffs in `LEAD_UPDATED` history. |

## 3. RevenueOS Success / Feedback Toast

| | |
|---|---|
| **Current implementation** | `components/ui/Toast.tsx`: `ToastProvider` + `useToast().show(message, icon?)`; items auto-removed after 3.2 s; stack `.toast-stack` bottom-right (desktop) / full width bottom (≤640 px); reduced motion handled; z-index 200 (above modals at 100). 67 call sites in 37 files. |
| **Exact gaps** | (1) No live region: nothing is announced to a screen reader. (2) No variants: icon only; `alert` is used for real errors (11) but also for neutral info (QuickActions "No phone number on file", UserMenu placeholders) and `close` for successful destructive completions (Lost, cancelled, rejected). (3) No manual dismiss, no pause on hover/focus, so a long API error can vanish unread in 3.2 s. (4) No stack cap and no de-duplication. (5) Inconsistent wording: "Nothing changed" shown with a success tick. (6) Silent successes: dashboard stage moves and Lead Pipeline status moves show a toast only on failure. (7) Mobile: full width but no safe-area offset and no keyboard consideration. |
| **Classification** | Provider, container, CSS, `useToast`: **Extend**. A second notification system: **Out of scope / not created**. Existing 67 calls: **Reuse unchanged** (the legacy `show(message, icon)` keeps working). Call-site migration: only where the inferred variant would be wrong or a flow is silent. |
| **Proposed design** | API: `toast.success(msg, opts?)`, `toast.error(msg, opts?)`, `toast.info(msg, opts?)`, plus the unchanged `toast.show(msg, icon?)` which infers a variant (`alert` → error, anything else → success). Behaviour: success/info 4 s, error 8 s and never auto-closed while hovered or focused; every toast has a dismiss button (44 px target on touch); newest at the bottom of the stack, max 3 visible (older ones leave first); an identical message within 1.5 s is not shown twice; Escape dismisses the focused toast. Accessibility: two live regions present in the DOM from first render (`role="status"` polite for success/info, `role="alert"` assertive for errors) so announcements are reliable; toasts never take focus; colour is never the only signal (icon + the variant word for screen readers). Layout: bottom-right on desktop (as now); full width above the bottom safe area on mobile; variant accent/contrast checked in light and dark-v4. The pure state transitions (add, dedupe, cap, expire, dismiss, pause/resume) live in a reducer that is unit-tested; timers stay in the provider. |
| **Workflows that adopt it in M2** | (a) Opportunity stage moves on the detail page (already toast; moved to the new API, Lost/Won wording) and on the dashboard board (success toast added; errors keep the message). (b) Lead create/edit/location (new flows). (c) QuickActions (4 calls) and UserMenu placeholders → `toast.info`. (d) "Nothing changed" cases → `toast.info`. (e) Lead Pipeline status move: add the success toast, errors through `toast.error`. (f) API-error toasts in the Lead and Opportunity pages → `toast.error`. **Not touched:** payment/Collections flows (M1 is closed; they keep working through the legacy `show`), and the other ~50 call sites, which keep their current behaviour and gain the new accessibility, dismissal and stacking for free. |
| **Backend / schema / permissions / migration** | None. |
| **Tests** | Reducer unit tests (cap, dedupe, expiry per variant, pause/resume, dismiss); static-markup tests for the provider (live regions exist when empty, roles per variant, dismiss labels, legacy `show` icon→variant mapping); a source guard that no second notification mechanism exists and that the migrated call sites use the new API; existing suites unchanged. |
| **Browser verification** | Success/info/error from real flows, auto-dismiss timing, hover/focus pause, dismiss by click and Escape, stacking of three quick actions, screen-reader announcement check by reading the live-region DOM, mobile (390) placement over a bottom sheet, light/dark contrast, reduced-motion. |
| **Real-DB activation** | Frontend-only; no activation step beyond the frontend rebuild. |
| **Explicit exclusions** | A sound/push/email notification system; a persistent notification centre (the existing Notifications page is separate); converting all 67 call sites; changing Payment Collection screens; a global application redesign. |

## 4. Cross-cutting

**Backend change is required** (two additive migrations and DTO/service changes). The frontend-only rule in `CLAUDE.md` is read-only for the backend; M1 set the precedent of a backend checkpoint approved first. This plan therefore asks for approval of a backend checkpoint explicitly (CP1 below).

**Proposed checkpoints (one commit each, stop for review after each):**

| CP | Content | Repo |
|---|---|---|
| CP1 | Backend: stage remark column + DTO/service; lead location columns + DTO/service + ISO country constants; two idempotent migrations (with rollbacks); jest + scratch-DB HTTP/integration verification; real-DB read-only reconciliation. Not applied to the real DB. | backend |
| CP2 | Frontend: Toast extension (reducer, live regions, variants, dismiss/pause/stack) + adoption in the stage flows, QuickActions, UserMenu, Lead Pipeline. | frontend |
| CP3 | Frontend: `OpportunityStageDialog`, remark through hooks/repositories (real + mock), dashboard drop flow, history rendering. | frontend |
| CP4 | Frontend: `Combobox`, geo datasets + parity, location in New/Edit Lead, list filters/search/detail, `uiContext.city` removal, contact helper wired into QuickActions (if D3 yes). | frontend |
| CP5 | Real-DB activation and verification (preflight, backups, both migrations, client regeneration, rebuild/restart, read-only + refused-write checks, fingerprints), exactly as CP3 of M1, with no real lead/stage mutation. | ops |

The order puts Toast first because stage and lead flows use it; CP2–CP4 can be reviewed together if you prefer fewer stops.

**Real-DB invariants for CP5:** whole-DB fingerprint before/after must differ only in `LeadTimeline` and `Lead` row text (the two new columns; old-column projections identical), no `PaymentCollection`/receivable/ledger change, no new lead or stage event created during verification.

## 5. Decisions needed before CP1

- **D1 — remark storage.** New nullable column `LeadTimeline.userRemark` (recommended: clean, no parsing, queryable) vs appending the remark to the existing `remarks` sentence (no schema change, but brittle to parse and mixes system and human text).
- **D2 — is location required?** Recommended: optional at the API (WhatsApp/webhook leads arrive without it) and asked-for in the manual New Lead form with country (and state for India) required there; alternative: fully optional everywhere.
- **D3 — contact helper.** Recommended: include `contactNumber(phone, country)` in QuickActions in CP4 (fixes wa.me for nationally typed Indian numbers on leads that have a country; unknown country unchanged). Alternative: provide the data only and leave the links as they are.
- **D4 — dashboard board.** Recommended: every drop opens the stage dialog (today only Won does).
- **D5 — `userRemark` visibility** follows the existing timeline permissions; confirm no extra restriction is wanted.
- **D6 — Toast API shape** as proposed (`success/error/info` plus the legacy `show`).

## 6. Risks

- Two new datasets (countries with calling codes) must be correct; a parity test between backend codes and frontend list, and a fixed snapshot, guard drift.
- Removing `uiContext.city` touches the mock seed, the list filter and several tests; the demo (mock) mode keeps working with real-shaped fields.
- `LeadTimeline` is read by many screens; the new nullable column is additive and defaulted to null.
- Existing phone data is unclean; the helper never rewrites it and never guesses.
- The dashboard UX change (dialog on every drop) slows a quick drag; it is the point of the feature and matches the detail page.
